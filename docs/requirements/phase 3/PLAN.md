## Approach

- Preflight both publishers: read configurations/history and analytics/event partitions, verify expected empty state and valid attribution memberships, and refuse conflicts before writing.
- **First define the Prebid integration and impacts:** pin Prebid.js 11.41.0 with Price Floors/Currency modules; complete an inventory of every populated field and relevant inherited default, including type/unit, scope/precedence, publisher/operator impact, site-visitor impact, and support classification. Each field must be behaviorally modeled, validated/inactive, or explicitly excluded—not decorative configuration ignored by the simulator. Use the concrete profile and impact matrix in `PREBID-CONFIGURATION.md`.
- Store canonical `setConfig`, `adUnits`, supported declarative `bidderSettings`, and `requestBids` options in immutable versioned snapshots. Keep publisher/version/user attribution in the application envelope. Derive existing product summaries (`floorCpm`, `auctionTimeoutMs`, `enabledBidders`, `currency`) from these snapshots, never as conflicting independent inputs. Function callbacks/adapters remain registered code; never execute functions from stored JSON.
- Build and validate the deterministic configuration timeline **from that profile**, then simulate/verify candidate data before database writes. Conditionally store current configurations and immutable history, read the stored snapshots back, and generate/load events by resolving their effective parameters. Do not alter configuration merely to force aggregate totals.
- Use five fictional bidder IDs (`atlas`, `beacon`, `cedar`, `delta`, `ember`) as **registered mock Prebid adapters**, with documented adapter-specific synthetic placement parameter contracts, not purported real SSP adapters/credentials. Separate private demand/latency distributions from native Prebid settings. Use three banner ad units per publisher with valid `code`, `mediaTypes.banner.sizes` and `bids` definitions; select one opportunity via `requestBids.adUnitCodes` per auction.
- Baseline: fixed bidder sequence; five independent synthetic origins; `maxRequestsPerOrigin: 4` (no contention); no cached bids, deals, PBS, IDs, sync traffic or CMP; USD-only fixed rates; medium price granularity; send-all-bids enabled; no bid adjustments. Floor enforcement is enabled for all client-side mock bidders with skip rate zero. Document absent features and their impact rather than claiming to simulate every optional Prebid module.
- Publisher A: set `setConfig.bidderTimeout` to **1,000 ms**, all five adapters in each selected ad unit, and a Price Floors USD banner rule/fallback of **$0.80**. Update the canonical rule/fallback to **$1.40** at analytical Week 4; latest configuration retains it. Use `floors.data.schema/values/default` with JS enforcement, not an invented top-level `floorCpm` or standalone `floorMin`.
- Publisher B: equivalent standards-shaped profile with **$0.60** banner floor and **900 ms** timeout; record initial settings. Keep settings constant through latency/traffic scenarios so those effects are not confused with configuration changes. Do not invent unrelated saves just to populate history.
- Each history entry contains synthetic updating-user attribution, ordered versions, exact timestamp, and before/after settings. Initial history has `before: null`; current configuration equals the final history state. Clearly document that attribution describes synthetic history, not an actual user action.
- Snapshot configuration at auction initiation; changes never retroactively affect an in-flight auction. Store version, resolved timeout, selected unit/size and stable auction/opportunity/request links. For each offer record original/normalized/adjusted CPM, floor rule/value/currency and enforcement/skip outcome, arrival/cutoff, targeting bucket, and rejection/eligibility reason. Apply units, size compatibility, deadline, expiry and floor rules in the pinned reference order.
- Verify one-knob-at-a-time **nonpersisted counterfactuals** with identical demand streams: floor, timeout, bidder inclusion, ad-unit selection, floor bypass/enforcement, price granularity and send-all targeting. Explain which alter auction winners/revenue versus only targeting/diagnostics. Keep revenue/visitor-impact claims bounded by actual modeled mechanisms, with auction wait/unfilled outcomes as proxies—not invented LCP/viewability or legal-compliance claims.

### 2. Deterministic simulation and scenario windows

Use a small seeded PRNG built with standard TypeScript/Node facilities; no new dependency. Fix a default seed and generator version. Seed publisher/day streams independently, use stable IDs and deterministic iteration/tie-breaking, and never use wall-clock time or `Math.random()` in dataset content. Record seed, version, boundaries, volume settings, and content hashes in a public dataset descriptor; keep root causes/expected answers only in the private manifest.

Generate intraday/weekend traffic patterns, bidder no-bids/timeouts, variable CPM/latency, floor-rejected offers, late arrivals, and unfilled auctions **by applying the canonical Prebid configuration**, not by writing desired metric totals. Preserve `bidResponse` vs `bidRejected`, timeout and auction-end outcomes. The baseline assumes zero event-loop timer jitter; lateness follows the recorded auction cutoff, not a universal claim that actual Prebid always closes at the nominal timeout.

Select the highest eligible candidate with deterministic tie handling and generate valid targeting. A candidate is not automatically `bidWon`: explicitly simulate the isolated ad-server/render step (no competing real ad-server line items), with positive TTL and fixed render delay, before emitting a win. All lifecycle/request/offer/render events stay inside the dataset bounds. Reserve a valid final rendered win exactly at the requested cutoff. Track original CPM separately from bucketed targeting; estimate revenue from the rendered win's recorded CPM, never from `hb_pb`.

**Analytical weeks use UTC calendar dates**, matching existing date-only tools. Week 1 is August 24–30 (first day partial); Weeks 2–8 are August 31–October 18. October 19 is a separate partial tail. The exact event span touches **57 UTC date buckets**, not 56 complete calendar days. Label both boundary days; do not extrapolate their totals into complete days.

| Publisher / window                | Controlled pattern and verification                                                                                                                                                                                                            |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A, Weeks 1–3                      | Stable/slightly growing demand and estimated revenue; explicitly account for partial Week 1.                                                                                                                                                   |
| A, Week 4: September 14–20        | Floor changes at `2026-09-14T00:00:00Z`. Week 4 estimated revenue is 16–20% lower than complete Week 3 (September 7–13), targeting 18%; traffic remains within 5%, fill decreases, winning CPM increases modestly.                             |
| A, Weeks 5–8                      | Lower performance persists with the elevated floor; no unexplained additional anomaly.                                                                                                                                                         |
| B, Weeks 1–3                      | Healthy baseline except `ember`, the consistently weak bidder.                                                                                                                                                                                 |
| B, Weeks 4–5: September 14–27     | `beacon` latency worsens beyond the unchanged 900 ms timeout. Late-response share rises materially (target ≥20 percentage points vs Weeks 2–3); its on-time participation and revenue contribution fall. Keep demand/traffic otherwise stable. |
| B, Week 6: September 28–October 4 | Beacon returns to baseline; use this full week as the clean comparison for the next scenario.                                                                                                                                                  |
| B, Weeks 7–8: October 5–18        | Traffic falls approximately 10–15% vs Week 6 while stronger demand improves fill and winning CPM; weekly estimated revenue grows at least 5%. No overlapping latency incident.                                                                 |
| B, whole span                     | `ember` response rate ≤25% and win rate ≤3% of requests; meaningfully worse than healthy peers.                                                                                                                                                |

Tune the bid/response distributions deterministically until the fixed default dataset passes these assertions; **never patch summary metrics or introduce fake wins to meet targets**. Preserve zero-response/no-fill observations. Scenarios remain discoverable through ordinary configuration and analytics tools; the private manifest is not an input to runtime answers.

### 3. Persistence and derived metrics

Reuse `${prefix}-publisher-data`; all keys are publisher-scoped:

- `PK=PUBLISHER#<id>`, with distinct SK prefixes for current configuration, timestamped history, daily metrics, daily bidder metrics, and a dataset descriptor/status.
- Under the user-approved revision, auction records use date-partitioned `PK=PUBLISHER#<id>#AUCTIONS#<UTC-date>` and stable timestamp/auction-ID sort keys. Legacy `#EVENTS#<UTC-date>` records remain readable; do not migrate or delete the retained partial test tables. Keep publisher metadata at the existing `METADATA` key, unchanged.
- Store one uncompressed auction under the existing `data` envelope, retaining initiation/end and five bidders' detailed observations. Validate decoded records through shared schemas and enforce the item-size limit before writes. Read-only queries derive publisher keys from trusted identity, never tool arguments; event-facing reconciliation expands and globally sorts each UTC day's observations.
- All DynamoDB Query paths paginate through `LastEvaluatedKey`; repository reads remain bounded by the existing maximum 90 UTC dates and five configured bidders. No table scans in normal tool execution.
- Load auction items in batches of at most 25; retry unprocessed items with capped backoff and fail clearly on exhaustion. Batch limits count physical items, not their logical events. Generate/write and expand/reconcile by UTC date instead of accumulating the entire dataset in RAM.
- Conditionally claim each empty dataset with `loading` status before writes. Mark datasets `ready` only after configuration, event, and aggregate checks pass. Database tools must not serve incomplete datasets. On interruption/failure, report the affected publisher/status; rerunning refuses it and requires deliberate operator review. No automatic rollback/delete, and no cleanup of the retained partial test tables.
- Implement reusable event aggregation and `data:reconcile` over the stored configuration/event timeline. Replace derived aggregate records by stable keys, not increments; reconciliation is rerunnable even though seeding is one-time.
- Validate lifecycle/request→accepted/rejected offer→candidate→rendered win chains, configured adapter/params/size, snapshotted version, actual cutoff, floor signaling/enforcement and skip logic, currency/adjustment ordering, TTL, targeting, unique identities, and one rendered win per opportunity. Floor-rejected offers are `bidRejected`, not accepted `bidResponse`; late/no-bid/timeout outcomes are distinct. Preserve observable normalized outcomes without claiming they are literal untouched hook payloads.
- Define **eligible opportunities** as opportunities configured to solicit bids, not opportunities that received an eligible response. All generated opportunities are eligible, so an increased floor reduces fill rather than its denominator. Retain every no-response/no-win opportunity through its requests.
- Daily totals: distinct auctions/opportunities, filled opportunities, winning CPM sum, estimated revenue = sum winning CPM / 1,000, weighted winning CPM, fill rate and synthetic auction-wait proxy. Bidder totals: requests, observed offers (accepted + rejected, counted once), accepted/rejected/eligible/late offers, timeouts, wins, latency, revenue. Explicitly label the existing response rate as **observed offers / requests**, not the literal number of `bidResponse` hooks; extend output/count schemas without double-counting rejected/late observations.
- Represent generated CPM in integer micro-CPM units internally, sum integers, then convert for shared/API output. Derive all revenue from winning events, use declared numerical tolerances when comparing serialized floating values, and keep null ratios for zero denominators.
- Reconcile bidder win/revenue sums against daily totals and daily totals against raw events, including boundary days. Never label `bidWon` as paid revenue.
