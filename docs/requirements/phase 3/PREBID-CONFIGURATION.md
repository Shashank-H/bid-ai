# Phase 3 — Prebid.js configuration and parameter impacts

## Standards baseline

Use **Prebid.js 11.41.0**, the stable release published October 8, 2026, as the reference, not mutable `master` (currently a prerelease). Lock version/build modules and adapter identities in dataset metadata. The inspected release resolves to commit `e9c437d7ddefcb5c1482b118c2a2f85432746bdb`; source evidence below is commit-pinned (accessed October 14, 2026). This is a standards-shaped synthetic banner integration, not a deployment with working SSP credentials or an actual publisher ad server.

## Canonical snapshot

Store separate `setConfig`, `adUnits`, supported declarative `bidderSettings`, and `requestBids` options in each version/history snapshot. Store selected modules and mock-adapter specifications alongside them. Inventory every explicitly populated nested field, plus every relevant inherited default, with its type, unit, scope/precedence, source, effect and simulator support. Reject unknown fields in this bounded profile; do not claim to implement all optional Prebid modules.

Recommended initial `setConfig` for Publisher A (B differs in timeout and floor):

```json
{
  "debug": false,
  "bidderTimeout": 1000,
  "bidderSequence": "fixed",
  "maxRequestsPerOrigin": 4,
  "useBidCache": false,
  "ttlBuffer": 1,
  "priceGranularity": "medium",
  "enableSendAllBids": true,
  "deviceAccess": false,
  "userSync": { "syncEnabled": false },
  "currency": {
    "adServerCurrency": "USD",
    "granularityMultiplier": 1,
    "rates": { "USD": { "USD": 1 } }
  },
  "floors": {
    "enabled": true,
    "skipRate": 0,
    "enforcement": {
      "enforceJS": true,
      "enforceBidders": ["*"],
      "enforcePBS": false,
      "floorDeals": false,
      "bidAdjustment": true
    },
    "data": {
      "currency": "USD",
      "schema": { "fields": ["mediaType"], "delimiter": "|" },
      "values": { "banner": 0.8 },
      "default": 0.8
    }
  }
}
```

Validate this profile against the pinned implementation in the offline compatibility harness before treating it as an executable configuration. Price Floors and Currency are explicitly selected modules; no external floor/rate fetch. `floorMin` is omitted: it is a minimum over matched rules, **not** the way to define a standalone static floor. Static rules are deliberate for a controlled experiment, not a recommendation for a production yield strategy.

Three ad units: stable `code`, `mediaTypes.banner.sizes` (e.g. `[[728,90]]`, `[[300,250]]`, `[[300,600]]`), and `bids` entries with `bidder` and adapter-specific `params`. Each fictional bidder is a **registered test adapter** with a documented parameter contract such as a synthetic `placementId`; fictional names/params must not be passed off as working production adapters. Select exactly one code via `requestBids.adUnitCodes` for each generated opportunity. Omit auction timeout overrides so `bidderTimeout` controls the baseline. Record resolved timeout/selected ad unit on each auction. Keep the stored `requestBids` template empty; concrete selected code and stable auction ID are derived per auction, not permanently hard-coded in that template. Callbacks and registered adapter/functions are executable harness code, never evaluated from stored JSON.

All bids are banner, client-side, USD, non-deal, fresh and rendered after a small fixed positive delay in the controlled synthetic flow. Each positive offered bid has explicit TTL (e.g. 60 seconds), dimensions, `creativeId`, `netRevenue`, request identity and an inert mock creative. No cross-auction reuse, PBS, real identities, CMP tokens, or live network requests. `bidderSettings` remains empty (normal standard targeting, no price adjustment) in the baseline.

## Event semantics and configuration-derived simulation

1. Resolve the immutable configuration snapshot at auction initiation; normalize its selected ad units, enabled adapters, currencies, floor rule and effective timeout. Settings changes during a running auction do not retroactively alter it.
2. Generate adapter offers/no-bids and dispatch/arrival times from private deterministic demand/latency distributions. These distributions are simulation inputs, **not fake `pbjs.setConfig` parameters**.
3. Track auction initiation/end and real eligibility cutoff. Prebid timers can close later than the nominal budget in a busy event loop; the default simulator explicitly assumes zero timer jitter and documents this simplification. Counterfactual harness checks verify boundary behavior rather than asserting that real Prebid always excludes `latency > bidderTimeout`.
4. Distinguish accepted `bidResponse`, floor `bidRejected`, `bidTimeout` and adapter no-bid/done outcomes. A floor-rejected offer must not be mislabeled as a Prebid `bidResponse`. Conversely, a late offer can still be added as a native `bidResponse` after `auctionEnd`; freeze this simulator's targeting/candidate at auction completion, record late observation separately, and do not invent a native late-rejection event. Retain arrival/latency/CPM and actual rejection reasons; [accepted/rejected/no-bid behavior](https://github.com/prebid/Prebid.js/blob/e9c437d7ddefcb5c1482b118c2a2f85432746bdb/src/auction.ts#L569-L663).
5. Derive currency-normalized/adjusted CPM, matched floor and targeting bucket; choose the highest eligible candidate with deterministic tie handling. Floor equality passes (rejection is strictly below floor). Default desirability equals adjusted CPM; no desirability override is enabled. Preserve original offered CPM, comparison CPM and bucketed `hb_pb` as separate values. Native tied-bid ordering is not guaranteed to match synthetic identifier ordering; avoid ties in the reference sample or document the synthetic tie policy.
6. An auction candidate is **not automatically a `bidWon`**. The isolated synthetic ad-server/render step selects/renders the highest eligible candidate with a controlled fixed delay; only then record a win. Native `bidWon` itself does **not** guarantee successful rendering: [the pinned event is fired for rendering, successfully or not](https://github.com/prebid/Prebid.js/blob/e9c437d7ddefcb5c1482b118c2a2f85432746bdb/src/adRendering.ts#L32-L45). Record an explicit synthetic successful-render outcome for generated wins, and inspect `adRenderSucceeded`/`adRenderFailed` separately in the reference. No actual ad-server competition, payment or visitor measurement is implied.
7. Derive metrics from those event/outcome records. Count each logical offered bid once across acceptance/rejection/late observations; expose accepted, rejected and late counts separately. Keep the existing `responses / requests` metric clearly defined as observed offers, not a literal count of `bidResponse` hooks. Wins/revenue arise only from synthetic rendered `bidWon` events.

## Configuration sensitivity verification

Use **bounded, nonpersisted paired experiments**, with identical demand/arrival streams and one supported knob changed. Do not add unrelated configuration changes to the eight-week history merely to exercise parameters.

- Raising/lowering floor changes eligibility/fill and possibly winners; no-response demand remains unchanged unless a declared floor-aware adapter model changes its response behavior.
- Increasing timeout admits otherwise late offers where the auction remains open and increases potential waiting; decreasing it excludes those offers. Check equal-to-deadline ordering against the reference harness.
- Removing a bidder removes requests/offers and can change competition; selecting a different ad unit changes valid sizes and slot identity.
